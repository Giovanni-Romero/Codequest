1. O que foi construído

Cinco telas, três widgets e uma folha de estilo. O jogo passou de "um motor com CLI" para algo que alguém abre e joga: 

$ python -m codequest ui

Menu de linguagem, quatro slots de save, mapa de ilhas com desbloqueio progressivo, tela de missão com editor e resultados, painel de dicas, tela de configuração. Tudo navegável só pelo teclado, com a paleta de carta náutica noturna que o documento de arte fixou antes de existir uma linha de CSS.

E, principalmente: zero lógica de jogo. Nenhuma tela calcula XP, decide desbloqueio ou compara resposta com esperado. Elas chamam os serviços que já existiam e renderizam a resposta.

2. A analogia: a vitrine e o estoque

Uma loja tem vitrine e estoque. A vitrine muda toda estação: manequim novo, iluminação nova, arrumação nova. O estoque não muda por causa disso — as caixas continuam onde estavam, com o mesmo conteúdo e o mesmo sistema de contagem.

Se o vendedor da vitrine começar a anotar quantidades num caderno próprio, a loja passa a ter duas contagens. Elas vão divergir, e o dia em que divergirem ninguém vai saber qual está certa.

A regra de camadas do CodeQuest é exatamente isso: a vitrine pode ser refeita inteira, desde que ela nunca guarde a contagem. É o que permite dizer, sem bravata, que trocar a interface por uma web não tocaria em nada abaixo dela.

3. Teoria 1 — A UI é descartável, e isso é o produto

A regra que governa esta fase estava escrita antes de a fase começar:

Regra de camada

tui/ importa apenas services/ e models/. Nunca engine/, nunca storage/.

Isso levantou um problema concreto na primeira hora: alguém precisa abrir a conexão SQLite, e a UI não pode. A solução foi um seam novo:

src/codequest/services/bootstrap.py

@dataclass(frozen=True, slots=True)
class GameContext:
    """Everything a front end needs, wired together and ready to use."""

    settings: Settings
    missions: MissionService
    progress: ProgressService
    session: GameSession
    connection: sqlite3.Connection

services/ pode conhecer storage/. A UI recebe o GameContext pronto e nunca descobre que existe um banco de dados. A CLI usa a mesma função, então as duas interfaces são ligadas de forma idêntica.

O teste que torna isso real

A regra não vive num documento. tests/integration/test_architecture.py percorre a AST de cada arquivo e falha se um import proibido aparecer. Escrever a Fase 4 inteira com esse teste ligado significa que a violação seria pega no minuto em que fosse cometida, não numa revisão futura que talvez nunca aconteça.

E há uma prova mais forte, que a Fase 5 permitiu fazer: renomear src/codequest/mentor/ e rodar a suíte inteira. O conjunto de falhas foi idêntico com e sem a pasta. Isso não é um argumento sobre a arquitetura, é uma medição dela.

4. Teoria 2 — Não bloquear o loop de eventos

Uma interface é um laço: pega evento, processa, redesenha, repete. Milhares de vezes por segundo. Se qualquer processamento demorar, o laço para — e uma janela parada é indistinguível de uma janela travada.

No CodeQuest, apertar F5 dispara um subprocess por caso de teste. Oito casos, alguns segundos. Na thread da UI isso é a tela congelada.

src/codequest/tui/screens/mission.py

@work(thread=True, exclusive=True)
def _run_attempt(self, code: str) -> None:
    def report(done: int, _total: int) -> None:
        # Widgets may only be touched from the UI thread, so hop back for each update.
        self.app.call_from_thread(self._show_progress, done, total)

    outcome = context.session.attempt(..., on_case=report)
    self.app.call_from_thread(self._show_outcome, outcome)

Por que barra determinada e não spinner

Um spinner diz "estou trabalhando". Uma barra diz "caso 3 de 8". O motor já sabia o total — usar spinner seria esconder informação que temos, e a regra está no documento de arte:

O motor sabe quantos casos existem, então um spinner esconderia informação que ele já tem.

Isso exigiu um parâmetro novo no motor. Opcional, com default None, de modo que a CLI e todos os testes existentes continuaram funcionando sem alteração — e com uma proteção que vale notar:

src/codequest/services/game_session.py

if on_case is not None:
    # A misbehaving observer must not fail an attempt that actually ran. The
    # progress bar is decoration; the verdict is the product.
    with contextlib.suppress(Exception):
        on_case(index, total)

5. Teoria 3 — Estado compartilhado entre threads

Tirar o trabalho da thread da UI resolveu o congelamento e criou um problema novo, que é o assunto mais transferível desta fase.

O erro, literal

SQLite objects created in a thread can only be used in that same thread. The object was created in thread id 5148 and this is thread id 25240.

A conexão nasceu na thread principal. O worker roda a tentativa e persiste o resultado, então toca a conexão de outra thread. O sqlite3 do Python bloqueia isso por padrão.

A saída preguiçosa seria desligar a checagem e seguir. A saída correta tem duas partes, e a segunda é a que importa:

src/codequest/storage/db.py

# check_same_thread=False because the UI runs an attempt on a worker thread and that
# attempt persists its result. Python's default guard assumes one connection per
# thread; the underlying library here reports threadsafety 3 (serialized), so sharing
# a connection is supported. What is *not* automatic is transaction interleaving, so
# ProgressService serialises its writers with a lock. Dropping the guard without
# adding that lock would trade a loud error for a rare corrupted save.
connection = sqlite3.connect(path, isolation_level=None, check_same_thread=False)

A distinção fina: sqlite3.threadsafety == 3 significa que a biblioteca serializa statements individuais. Não significa que a sua transação de quatro statements seja atômica em relação a outra thread. Conceder XP toca attempt, progress, profile e possivelmente unlocked_island; revelar uma dica escreve em progress. As duas podem acontecer ao mesmo tempo.

src/codequest/services/progress_service.py

self._lock = threading.RLock()
...
with self._lock, transaction(self.connection):
    ...
[AI-ENG:shared-state]

Essa armadilha aparece na primeira vez que um agente dispara chamadas de ferramenta em paralelo. O cliente HTTP é thread-safe, o driver do banco é thread-safe, e a sua operação de vários passos não é — porque ninguém prometeu que seria.

A pergunta a fazer: "o que aqui é uma sequência que precisa ser indivisível?" A resposta quase nunca é "nada". Bibliotecas garantem a atomicidade das operações delas; a atomicidade da sua operação é sua.

6. Teoria 4 — Testar interface sem abrir os olhos

Interface é onde suíte de teste costuma apodrecer, e a razão é que a maioria das tentativas testa a coisa errada. Esta fase usa duas técnicas, que respondem perguntas diferentes.

Pilot: o programa funciona?

A API run_test() do Textual sobe o app sem terminal, envia teclas de verdade e deixa você inspecionar os widgets. Testa comportamento:

tests/integration/test_tui_flow.py

async def test_two_hints_then_solving_pays_the_discounted_xp(app):
    """A regra da Fase 3, chegando ao jogador pela interface pela primeira vez."""
    async with app.run_test() as pilot:
        await _open_mission(pilot)

        await pilot.press("f1")
        await pilot.press("f1")
        await pilot.pause()

        pilot.app.screen.query_one("#editor", CodeEditor).text = CORRECT_SUM_LIST
        await pilot.press("f5")
        await pilot.pause(delay=6)

        profile = pilot.app.context.progress.profiles.get_by_name("giovanni")
        assert profile.total_xp == 7

Repare no que esse teste cobre: uma regra de negócio da fase anterior, verificada atravessando a interface inteira. É teste de integração de verdade, não de widget.

Snapshot: continua parecendo o que foi desenhado?

Cada tela é renderizada em SVG e comparada com uma imagem guardada. Pega o que o pilot não vê: uma borda que sumiu, uma cor que tornou "bloqueado" indistinguível de "disponível", uma faixa responsiva que parou de refluir.

O risco de snapshot, dito por inteiro

Snapshot é o teste mais fácil de desligar por acidente. Roda --snapshot-update, o vermelho vira verde, o commit passa — e agora o teste aprova qualquer coisa.

A disciplina é olhar o diff antes de aceitar. Nesta fase, adicionar a tecla F2 ao rodapé mudou 5 dos 10 snapshots, e os outros 5 passaram intactos. Esse "5 e não 10" é a informação: o raio da mudança bateu com a edição. Se os 10 tivessem mudado, alguma coisa mais funda teria acontecido.

7. Os quatro bugs que só a interface encontrou

Trezentos testes passavam antes desta fase. Todos os quatro bugs abaixo estavam lá esperando, invisíveis, porque nada tinha exercitado esses caminhos.

BugPor que estava escondido
SQLite recusou a worker thread A CLI é single-threaded. A restrição existia desde a Fase 2 e nunca tinha sido tocada
Widget._render já existe no Textual Quatro classes sobrescreveram com assinatura diferente. Quebra na hora de pintar, não na de importar — nenhum teste unitário pinta
O editor engolia F5 e Escape Um TextArea focado consome teclas. Como ele recebe foco ao abrir a missão, os controles do jogo paravam de funcionar sempre
ListView sem linha destacada Depois de reconstruir a lista, Enter não fazia nada. A lista parecia certa e simplesmente se recusava a abrir

E um quinto, de outra natureza: o extra textual[syntax] não estava no pyproject.toml. Sem ele, TextArea.code_editor(language="python") devolve um documento comum, sem destaque de sintaxe, sem levantar erro e sem avisar. O teste que pega isso não verifica o import:

tests/unit/test_editor_highlighting.py

def test_the_code_editor_really_parses_python():
    """The document must be syntax-aware, not merely constructed without error."""
    editor = TextArea.code_editor("def f(x):\n    return x + 1\n", language="python")

    assert isinstance(editor.document, SyntaxAwareDocument)
O padrão, que já apareceu quatro vezes neste projeto

PRAGMA foreign_keys desligado por padrão. resource.setrlimit ausente no Windows. O extra de sintaxe faltando. Em todos, a API entrega menos do que parece e não reclama.

O gatilho para desconfiar: sempre que uma capacidade depende de algo externo estar presente — pragma, syscall, extra de pacote, modelo baixado — o caminho degradado costuma ser o silencioso, porque quem escreveu a biblioteca preferiu funcionar mal a não funcionar.

A defesa é sempre a mesma e cabe numa frase: teste a capacidade, não o import. hasattr(TextArea, "code_editor") passava.

9. Exercícios

1. Por que tui/ não pode importar storage/, se a UI obviamente precisa de dados salvos?

Porque "precisar dos dados" e "saber como eles são guardados" são coisas diferentes. A UI precisa de um Profile; ela não precisa saber que ele veio de SQLite, de JSON ou de um servidor.

O benefício concreto não é abstrato: quando o XP parar de ser contado direito, existe um lugar onde a escrita acontece. Se a tela pudesse escrever, você teria que procurar um UPDATE perdido dentro de um widget.

2. O callback on_case engole qualquer exceção do observador. Isso não está escondendo bugs?

Está, de propósito, e a justificativa é a assimetria dos custos. Se o widget de progresso explodir, a alternativa é perder a tentativa inteira — segundos de subprocessos e um veredito válido — para mostrar uma barra.

A regra geral: um observador nunca deve poder derrubar o que observa. Vale igual para telemetria, logging e webhooks. O que falta aqui, e seria a melhoria honesta, é registrar a exceção em vez de descartá-la em silêncio.

3. sqlite3.threadsafety == 3 diz que a conexão pode ser compartilhada. Por que ainda precisa de lock?

Porque o nível 3 garante que um statement não corrompe outro. Não diz nada sobre uma transação de vários statements.

Conceder XP faz quatro escritas dentro de um BEGIN/COMMIT. Se outra thread abrir a própria transação no meio, na mesma conexão, o resultado é indefinido. A biblioteca garante a atomicidade das operações dela; a atomicidade da sua operação é sua.

4. Você vai construir uma interface de chat para um agente. Quais três decisões desta fase você copia primeiro?
  1. Nada de lógica de agente na UI. A tela envia a mensagem e renderiza o que voltar. No dia em que existir uma segunda interface — Slack, API, CLI — nada abaixo dela muda.
  2. A chamada nunca na thread que desenha. Uma resposta de LLM leva segundos. É o mesmo problema do F5, com o mesmo remédio, e é por isso que streaming é o padrão em vez de um luxo.
  3. Progresso determinado quando possível. Se o agente tem um plano de passos, mostre "passo 3 de 8". Um spinner é o que se usa quando não se sabe — usar quando se sabe é jogar informação fora.

E a quarta, que só se aprende apanhando: decida o que a tela mostra quando o modelo falha, antes de escrever o caminho feliz. É o assunto da Fase 5.
