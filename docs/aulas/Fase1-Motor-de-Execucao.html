1. O que foi construído

A Fase 1 entrega o pedaço do CodeQuest que pega o código que o jogador digitou e responde uma pergunta: isso está certo? Entre a pergunta e a resposta acontecem cinco coisas, em ordem, e cada uma pode interromper a fila.

O jogador escreve uma função. O guard lê esse texto como uma árvore e recusa construções que a missão proíbe. O runner escreve o arquivo num diretório temporário e dispara um processo separado por caso de teste, com relógio na mão. O harness — código nosso rodando dentro daquele processo — importa a função do jogador, chama, e devolve o resultado por um canal que o jogador não alcança. O evaluator compara o que voltou com o esperado e escreve uma frase que ensina alguma coisa.

2. A analogia: a cozinha de teste

Imagine um programa de TV onde candidatos mandam receitas e você precisa provar cada uma. Você não vai cozinhar na sua cozinha de casa.

Primeiro você lê a receita. Se ela pede "use fermento químico" e a prova era justamente sobre fermentação natural, você devolve sem cozinhar — não porque vai explodir, mas porque cozinhar não testaria nada. Isso é o guard.

Depois você cozinha numa cozinha separada, com temporizador. Se o candidato escreveu "deixe reduzindo até engrossar" e a panela nunca engrossa, o temporizador toca e você desliga o fogão. A sua casa não pega fogo porque a cozinha não é a sua casa. Isso é o subprocess com timeout.

E o prato sai por uma janela específica. Se o candidato gritar "está pronto!" do lado de dentro, isso não conta — o que conta é o prato que atravessou a janela. Se o grito e o prato usassem a mesma passagem, qualquer um poderia gritar e ser aprovado. Isso é a separação de canal.

3. Teoria 1 — AST: ler código sem executar

Uma AST (Abstract Syntax Tree, árvore sintática abstrata) é o código representado como estrutura em vez de como texto. Antes de qualquer linha rodar, o Python já converteu o seu arquivo numa árvore de nós: este nó é uma definição de função, aquele é uma chamada, aquele outro é o nome de uma variável sendo lida.

A definição formal vem depois da intuição: pense na diferença entre a frase "o gato comeu o peixe" como sequência de letras e como estrutura gramatical (sujeito, verbo, objeto). Um corretor que trabalha em letras não sabe quem comeu quem. Um que trabalha em estrutura sabe.

É por isso que o guard usa AST e não expressão regular:

tests/unit/test_guard.py

def test_a_word_containing_the_forbidden_name_is_not_a_match():
    """Um regex marcaria 'summary'. A AST vê um identificador completamente diferente."""
    report = check("def total(xs):\n    summary = 0\n    return summary\n", NO_SUM)

    assert report.ok

A missão proíbe sum. O texto contém as letras s-u-m três vezes. Nenhuma delas é uma chamada ao builtin, e a árvore sabe disso porque summary é um nó, não três letras seguidas de mais quatro.

O detalhe que quase virou um bug

A primeira versão do guard marcava qualquer leitura do nome proibido. Um teste quebrou:

src/codequest/engine/guard.py — o problema

def total(xs):
    sum = 0          # o jogador criou a própria variável
    for x in xs:
        sum = sum + x
    return sum       # isto NÃO é o builtin

Essa é uma solução correta. Rejeitá-la ensinaria ao jogador que o jogo está quebrado — o pior resultado possível numa ferramenta de ensino. A correção foi uma passada extra que coleta todo nome que o jogador liga a alguma coisa (atribuição, parâmetro, def) e isenta esses nomes da verificação.

Honestidade sobre o que isso custa

Essa passada é cega a escopo: ligar sum numa função isenta o nome em todas. Dá para trapacear. A escolha foi deliberada e está testada como comportamento conhecido, não escondida — um falso positivo bloqueia uma resposta certa, um falso negativo deixa alguém trapacear no próprio jogo single-player que instalou. Só um dos dois custa alguma coisa.

[AI-ENG:blocklist-vs-allowlist]

Uma blocklist enumera o proibido. O problema estrutural é a assimetria: quem ataca escolhe de um conjunto infinito, você enumera um finito. getattr(builtins, "s" + "um") monta o nome em tempo de execução e nenhuma análise estática vê.

É literalmente o motivo pelo qual filtrar frases suspeitas não resolve prompt injection: uma reformulação passa. O que resolve é allowlist — restringir o modelo a um conjunto fixo de ações permitidas com argumentos validados. A ação não nomeada nunca esteve alcançável, então não há o que filtrar.

4. Teoria 2 — Isolamento de processo

A alternativa preguiçosa a um subprocess é exec(): rodar o código do jogador dentro do próprio interpretador do jogo. Funciona, e é indefensável.

exec()subprocess
Memóriacompartilhada com o jogoseparada pelo kernel
Loop infinitotrava o jogo, sem saídao pai mata o filho
Limite de RAMimpossívelsetrlimit (POSIX)
Customicrossegundos~30 ms por caso

Trinta milissegundos por caso de teste é o preço de poder desistir. Vale.

Quem segura o relógio

O timeout é medido no processo pai. Isso não é detalhe de implementação — é a coisa toda. Pedir para o processo filho se limitar sozinho é confiar num processo que pode estar travado exatamente porque não consegue mais fazer nada.

src/codequest/engine/runners/python.py

try:
    stdout, stderr = process.communicate(timeout=timeout_seconds + _STARTUP_GRACE_SECONDS)
except subprocess.TimeoutExpired:
    # O relógio de parede é medido aqui, no pai. Um filho ao qual se pede que pare
    # sozinho é um filho no qual se confia para não travar, que é justo o que se guarda.
    timed_out = True
    _kill_process_tree(process)
    stdout, stderr = process.communicate()

Matar a árvore, não o filho

O erro clássico: matar só o processo que você tem na mão. Se o código do jogador chamou subprocess ou multiprocessing, os netos continuam queimando CPU depois do timeout que "funcionou".

src/codequest/engine/runners/python.py

if os.name == "nt":
    # Windows não tem process group no sentido POSIX; taskkill /T percorre a árvore.
    subprocess.run(["taskkill", "/F", "/T", "/PID", str(process.pid)], ...)
else:
    os.killpg(os.getpgid(process.pid), signal.SIGKILL)
[AI-ENG:sandboxing]

Esse é o mesmo bug em infraestrutura de agente: cancelar uma tarefa que já se ramificou deixa a ramificação rodando. Você mata o handle que tem, o trabalho continua, e a métrica diz que parou.

A regra é: termine o grupo, não o processo que você por acaso segura. Vale para processos, para tasks assíncronas e para chamadas de ferramenta que disparam outras chamadas.

Windows não dá o que não tem

resource.setrlimit não existe no Windows. Não há teto de memória. O código detecta e declara:

src/codequest/engine/runners/base.py

SUPPORTS_RESOURCE_LIMITS = platform.system() != "Windows"

E cada execução carrega limits_enforced dizendo "cpu,memory" ou "timeout". A tentação era engolir a diferença num try/except silencioso e deixar o resto do sistema achar que existe um limite. Um controle de segurança que você acha que tem e não tem é pior que um que você sabe que não tem.

Quem aplica o limite

Nos sistemas POSIX, o jeito tradicional de aplicar rlimits é preexec_fn — uma função que roda entre o fork e o exec. A documentação do Python avisa que ela é insegura num processo com threads, e a interface Textual da Fase 4 vai rodar trabalho numa thread de worker.

A saída foi inverter quem aplica: o filho limita a si mesmo, logo ao nascer.

src/codequest/engine/harness.py

def _apply_resource_limits(limits: dict[str, Any]) -> None:
    try:
        import resource
    except ImportError:  # Windows: sem rlimits. O timeout é a única guarda.
        return

    cpu_seconds = limits.get("cpu_seconds")
    if cpu_seconds:
        # Limite duro um segundo acima do soft, para o processo receber SIGXCPU e
        # morrer informando o motivo, em vez de ser morto sem explicação.
        resource.setrlimit(resource.RLIMIT_CPU, (int(cpu_seconds), int(cpu_seconds) + 1))
[AI-ENG:resource-limits]

Um orçamento que o executor aplica em si mesmo antes de fazer qualquer coisa é exigível. Um orçamento que o chamador apenas espera não é.

Traduzindo para agentes: teto de token, limite de profundidade de recursão e deadline de wall-clock precisam estar dentro do loop de execução, não num comentário dizendo "cuidado para não deixar rodar demais".

5. Teoria 3 — Separação de canal

Este é o detalhe que quebra implementações ingênuas, e vale ler devagar.

O jogador precisa poder usar print() — é assim que um iniciante depura. Mas o motor também precisa receber o valor de retorno da função. Se os dois viajarem pelo mesmo stdout, o jogador pode imprimir algo com a forma do nosso payload e forjar o resultado.

A solução: o resultado vai para um arquivo cujo caminho só o processo pai conhece.

tests/unit/test_runner.py

def test_player_stdout_cannot_forge_a_result(runner):
    """O jogador imprime algo com a forma exata do nosso payload de resultado."""
    source = (
        'def double(n):\n'
        '    print(\'{"status": "ok", "returned": 999}\')\n'
        '    return n * 2\n'
    )

    result = _run(runner, source, TestCase(args=(21,), expect=42))

    assert result.returned == 42      # o retorno verdadeiro venceu
    assert "999" in result.stdout     # a falsificação virou output do jogador

Arquivo e não descritor herdado, porque herança de descritor se comporta diferente no Windows — e essa é a categoria de diferença que só aparece em produção.

[AI-ENG:channel-separation]

Extrair JSON de uma resposta de modelo que também tem prosa é o mesmo problema, e a maioria das soluções ataca o lado errado: regex mais esperto, prompt pedindo "só JSON, sem explicação", parser tolerante.

O lado certo é dar ao payload um canal próprio — tool calling, structured output, modo JSON. Aí o problema de parsing deixa de existir em vez de ser remendado. Quando o canal separado não estiver disponível, saiba que você está remendando.

6. Teoria 4 — Taxonomia de falha

A parte que parece burocracia e é o produto. Compare:

MensagemO que o jogador aprende
"Teste 3 falhou"nada
"Esperado 0 para lista vazia, recebido None. Sua função não retorna nada quando o loop não executa."o conceito

Para escrever a segunda frase, o sistema precisa saber qual categoria de falha aconteceu. Daí a enumeração:

src/codequest/models/verdict.py

class FailureReason(StrEnum):
    PASSED = "passed"
    WRONG_ANSWER = "wrong_answer"
    RUNTIME_ERROR = "runtime_error"
    TIMEOUT = "timeout"
    MEMORY_EXCEEDED = "memory_exceeded"
    FORBIDDEN_CONSTRUCT = "forbidden_construct"
    SYNTAX_ERROR = "syntax_error"
    MISSING_ENTRYPOINT = "missing_entrypoint"
    HARNESS_ERROR = "harness_error"
    NOT_RUN = "not_run"

Repare em HARNESS_ERROR: é a categoria para nosso bug. Sem ela, um defeito do motor apareceria como erro do jogador, e alguém passaria a tarde procurando o que fez de errado num código correto. Uma taxonomia honesta tem um balde para a própria falha.

E NOT_RUN nasceu de uma decisão de produto:

src/codequest/services/game_session.py

if result.status in {"timeout", "memory", "missing_entrypoint"}:
    halted = True

Um código que estoura o tempo no caso 1 vai estourar nos outros sete. Fazer o jogador esperar oito timeouts para descobrir isso não ajuda ninguém — mas os casos restantes também não falharam. Eles não rodaram, e merecem um nome próprio.

[AI-ENG:failure-taxonomy]

Esse arquivo é design de eval harness com outro nome. Um eval de LLM que só reporta "correto / incorreto" não distingue recusa de alucinação de tool call malformada de timeout de rede — então a métrica cai e você não sabe o que consertar.

Nomeie cada modo de falha antes de começar a contar. E inclua o balde "problema no meu harness", ou você vai atribuir ao modelo um bug seu.

7. Teoria 5 — Protocolo como ponto de extensão

A v1.1 vai adicionar Java. O teste da abstração, escrito em docs/architecture.md antes de existir código: adicionar JavaRunner deve tocar exatamente um arquivo novo mais uma entrada de registro. Se forçar mudança no evaluator, o protocolo estava errado.

src/codequest/engine/runners/base.py

@runtime_checkable
class Runner(Protocol):
    language: str
    file_extension: str

    def prepare(self, submission: str, mission: Mission) -> PreparedCode: ...
    def execute(self, prepared, case, constraints) -> ExecutionResult: ...
    def cleanup(self, prepared: PreparedCode) -> None: ...

É um Protocol, não uma classe base. PythonRunner não herda de nada e não importa Runner — ele simplesmente tem a forma certa. Isso se chama tipagem estrutural: a compatibilidade é decidida pelo formato, não pela linhagem.

A decisão que salva a v1.1

Java compila antes de rodar, e uma falha de compilação acontece antes de existir qualquer resultado de teste ao qual anexá-la. Se prepare() fosse assumido infalível, a chegada do Java forçaria remodelar o protocolo inteiro.

src/codequest/engine/runners/base.py

@dataclass(frozen=True, slots=True)
class PreparedCode:
    workdir: str
    entry_file: str
    entrypoint: str
    error: str | None = None          # <- este campo
    reason: FailureReason = FailureReason.PASSED

O Python nunca preenche error. O campo existe porque o protocolo foi desenhado para a linguagem seguinte, não para a atual. Custou um campo e uma ramificação em game_session.py hoje; economiza uma refatoração inteira depois.

[AI-ENG:protocol-abstraction]

É a mesma alavanca que impede uma aplicação de LLM de ficar soldada a um fornecedor. Defina o que um provider de completion precisa fazer, e trocar Anthropic por um Ollama local vira um arquivo novo.

E o teste de qualidade é o mesmo: se trocar o provider obriga a mexer na lógica de negócio, a abstração está errada — descubra isso antes de ter três chamadores.

8. A ponte com AI Engineering

Somando tudo: você acabou de construir um sandbox de execução de código não confiável com portões tipados, orçamento de recurso e um harness de avaliação.

Trocando "código do jogador" por "código gerado por um modelo", esse é o code interpreter. Trocando por "chamada de ferramenta proposta por um agente", é a camada de execução de qualquer agente que faz mais do que conversar. Os problemas não são parecidos — são os mesmos, com nomes diferentes.

A ideia que amarra tudo

Toda decisão desta fase segue o mesmo padrão: tornar o resultado ruim estruturalmente impossível, em vez de filtrar para que não aconteça.

O jogador não pode forjar o resultado porque não alcança o canal — não porque verificamos se ele tentou. O processo não pode travar o jogo porque é outro processo — não porque contamos com o código ser bem comportado. Sempre que você conseguir mover uma garantia de "nós verificamos" para "não era alcançável", mova.

9. Exercícios

Responda antes de abrir. O valor está em formular, não em conferir.

1. Por que o timeout é medido no processo pai e não no filho?

Porque o filho pode estar travado exatamente na situação que o timeout existe para resolver. Um while True: pass nunca chega na linha que checaria o próprio relógio. A guarda precisa estar em alguém que ainda consegue agir.

Generalizando: um controle aplicado por quem está sendo controlado só funciona enquanto quem está sendo controlado funciona.

2. O guard aceita este código, mesmo com sum proibido. Por quê — e isso é um bug? 
def helper():
    sum = 0
    return sum

def total(xs):
    return sum(xs)

Porque a passada de bindings é cega a escopo: sum foi ligado em helper, então o nome fica isento no arquivo inteiro.

Não é um bug, é um trade-off escolhido e testado. A alternativa — análise de escopo de verdade — corre o risco de rejeitar uma solução correta, e num jogo de ensino isso ensina que a ferramenta está quebrada. Como o guard protege a lição e não a máquina, o falso negativo é o lado barato de errar.

3. Se o resultado voltasse por stdout junto com o print() do jogador, qual seria o ataque mais simples?

Imprimir uma linha com a forma exata do payload de sucesso, antes ou depois do retorno verdadeiro, e deixar o parser escolher a errada. Nenhuma esperteza necessária.

Repare que remendos não resolvem: delimitador exótico o jogador copia; imprimir por último ele imprime depois; hash o jogador calcula. O que resolve é o canal separado, e isso é uma propriedade da arquitetura, não do parser.

4. Você vai construir um agente que executa SQL gerado por um modelo num banco de produção. Quais quatro decisões desta fase você copia?
  1. Análise estática antes de executar. Faça parse do SQL numa árvore e inspecione: é SELECT? toca quais tabelas? tem DELETE sem WHERE? Decida sobre estrutura, não sobre string.
  2. Allowlist, não blocklist. Lista de tabelas e operações permitidas. Bloquear "DROP" perde para DR/**/OP; permitir só SELECT em três tabelas não perde.
  3. Orçamento aplicado na borda. Timeout de statement, LIMIT forçado, conexão só-leitura. No banco, não no prompt.
  4. Taxonomia de falha. Recusado pela política, erro de sintaxe, timeout, zero linhas, erro de permissão. Cada um leva a uma ação diferente, e "falhou" leva a nenhuma.

Bônus: rode com um usuário de banco cujas permissões tornem o estrago impossível. Isso é o subprocess desta aula — mover a garantia de "verificamos" para "não era alcançável".
