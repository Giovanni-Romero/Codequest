1. O que foi construído

Um painel de chat no canto da tela de missão. O jogador pergunta, um modelo local responde. Quatro arquivos, todos opcionais, e a regra que governa tudo:

O jogo tem que ser inteiramente jogável e inteiramente educativo com o Ollama desinstalado. Se apagar src/codequest/mentor/ quebrar qualquer coisa fora dessa pasta, a integração está errada.

O ensino já estava pronto antes desta fase: analogia, explicação, exemplo, três degraus de dica, tudo escrito à mão em YAML. O mentor não é o professor. É o colega ao lado.

2. A analogia: o colega de estudo

Duas pessoas podem te ajudar numa prova, e a diferença entre elas é tudo.

A primeira te passa a resposta. Você entrega, tira nota, e sai da sala sem saber fazer. Na próxima prova, a pessoa não está lá.

A segunda pergunta: "o que acontece se a lista estiver vazia?". Você para, pensa, e encontra o buraco sozinho. Levou mais tempo e você vai lembrar daqui a um mês.

O detalhe que essa analogia esconde, e que é o conteúdo técnico desta fase: você pode pedir à primeira pessoa que se comporte como a segunda. Ela vai concordar, e vai falhar em algum momento, porque a tentação de ajudar direto é forte. A única forma de garantir é ela não ter a resposta.

3. Teoria 1 — Prompt orienta, código decide

Esta é a lição mais valiosa do projeto inteiro para quem vai construir com LLM.

O system prompt do mentor diz, entre outras coisas:

src/codequest/mentor/policy.py

f"- Never write a function called '{entrypoint}'. That is the mission.\n"

Isso funciona. Reduz muito a frequência com que o modelo entrega a resposta. E é exatamente por funcionar quase sempre que é perigoso confiar nele: você para de pensar no caso em que não funciona.

A distinção

Um prompt desloca probabilidade. Um filtro decide.

Qualquer coisa que você precise garantir exige código de um dos lados do modelo. Qualquer coisa que você apenas prefira pode viver no prompt.

Então o mentor tem duas camadas de verdade, e o prompt não é nenhuma delas:

src/codequest/mentor/policy.py

def filter_reply(text: str, entrypoint: str) -> tuple[str, bool]:
    """Screen a reply before it reaches the player."""
    if defines_entrypoint(text, entrypoint):
        return REDACTION, True
    return text, False

O filtro é deliberadamente estreito

Ele procura uma definição de função com o nome do entrypoint, não a menção do nome: 

pattern = rf"^\s*(?:async\s+)?def\s+{re.escape(entrypoint)}\s*\("

Um mentor que não pode dizer "sum_list" não consegue fazer uma pergunta útil. Bloquear a palavra seria filtrar o sintoma errado — o que entrega o trabalho é a definição, não o substantivo. Há testes para os dois lados:

tests/unit/test_mentor.py

def test_merely_naming_the_function_is_allowed():
    """A mentor that cannot say the function's name cannot ask a useful question."""
    reply = "What should sum_list return when the list is empty?"

    text, redacted = filter_reply(reply, "sum_list")

    assert not redacted
    assert text == reply
[AI-ENG:guardrails]

Carregue essa distinção para toda feature com LLM. "Não invente fatos" no prompt reduz alucinação; um verificador que confere cada afirmação contra a fonte é o que garante. "Só responda sobre nossos produtos" reduz desvio; um classificador na entrada decide.

A pergunta que separa as duas: se isso falhar uma vez em cem, é aceitável? Se for, prompt basta. Se não for, você precisa de código — e precisa aceitar o custo de falsos positivos que vem junto.

4. Teoria 2 — Filtrar na fonte

A camada 1 é mais forte que a 2, e vale entender por quê.

A missão tem um campo solution com a resposta completa, e casos de teste escondidos com os valores esperados. Nenhum dos dois entra no contexto. Não são removidos depois — nunca são montados:

src/codequest/mentor/prompts.py

    What goes in, and why each field earns its place:

    - **system** - the role and the standing policy
    - **brief** - without it the mentor cannot tell right from wrong
    - **concepts** - lets it name what was taught instead of inventing vocabulary
    - **player code** - the actual subject of nearly every question
    - **last verdict** - where they are stuck, which is usually the whole answer
    - **hints used** - so it does not repeat a rung they already paid for

    What stays out, on purpose: ``mission.solution`` and the hidden test cases.

A diferença entre "filtrar na fonte" e "filtrar depois" é a diferença entre uma propriedade e um procedimento. Um dado que nunca foi enviado não pode vazar por prompt injection, por bug no filtro, por mudança de modelo ou por alguém que refatorou sem entender. Um dado enviado e filtrado depende de o filtro estar certo, para sempre.

E existe uma terceira camada, barata, que guarda contra o refactor descuidado:

src/codequest/mentor/policy.py

def is_safe_context(payload: str, mission_solution: str, hidden_values: list[str]) -> bool:
    """Assert that nothing forbidden made it into the assembled context.

    Belt and braces over the filtering that already happened at assembly time. Cheap, and
    the failure it guards against - a refactor quietly widening what gets sent - is
    exactly the kind that survives code review.
    """
Vale reparar em quem checa

Essa função é chamada pelos testes, não em produção. É uma asserção sobre o comportamento do sistema, não um filtro em tempo de execução.

A hierarquia inteira, do mais forte ao mais fraco: não montar > filtrar na saída > testar que não vaza > pedir no prompt. Use quantas camadas o risco justificar, e saiba qual é qual.

5. Teoria 3 — Contexto é orçamento

O reflexo de quem começa é mandar tudo. O modelo tem 128 mil tokens de janela, a missão cabe folgada, então por que escolher?

Três razões, e nenhuma é a janela:

CustoPor quê
AtençãoCada token irrelevante compete com os relevantes. Contexto mais longo com a mesma informação costuma dar resposta pior
LatênciaPrefill é proporcional ao tamanho. Num modelo local, num laptop, isso é a diferença entre útil e abandonado
Superfície de vazamentoTudo que entra pode sair. Este projeto é a prova: enviar a solution tornaria o mentor um botão de "revelar resposta"

O contexto real do CodeQuest tem cerca de 1.200 caracteres. Cada campo tem justificativa escrita no docstring. O campo mais valioso, aliás, não é o código do jogador:

src/codequest/mentor/prompts.py

    where = "a visible test" if failure.visible else "a hidden test"
    return f"Their last run failed on {where}. {failure.detail}"

Onde a pessoa travou costuma ser a resposta inteira. Um jogador que digita "não entendi" com um veredito de "esperado 0 para lista vazia, recebido None" anexado recebe ajuda muito melhor do que a pergunta merecia.

Repare também que essa linha não pode vazar o valor esperado de um caso escondido, e não porque alguém lembrou de tomar cuidado: ela lê o failure.detail, que o evaluator da Fase 1 já escreve sem o valor. A restrição se sustenta por construção.

[AI-ENG:context-assembly]

O exercício que transfere: pegue o seu prompt de produção e, campo por campo, responda "por que isto está aqui, e o que piora se eu tirar?". Todo campo sem resposta boa é candidato a sair.

Em RAG isso vira a decisão de quantos chunks recuperar. A resposta quase nunca é "o máximo que couber". Três chunks bons superam vinte medianos, e a diferença aparece nas perguntas difíceis, que são as que importam.

6. Teoria 4 — Falha é ramo normal

Nesta máquina, agora, o Ollama está instalado e parado. Esse é o estado real, e é por isso que ele é o primeiro caso tratado, não o último.

src/codequest/mentor/client.py

class MentorState(StrEnum):
    READY = "ready"
    THINKING = "thinking"
    OFFLINE = "offline"
    MODEL_MISSING = "model_missing"
    TIMED_OUT = "timed_out"
    ERROR = "error"

Quatro modos de falha, cada um com nome e mensagem própria. Isso é a taxonomia de falha da Fase 1 aplicada de novo, e a razão é a mesma: "algo deu errado" não é informação. 

Mentor offline. Ollama is not answering on http://localhost:11434.
Start it with `ollama serve`, or keep playing - the game teaches without it.

Compare com o que o servidor responde quando está de pé mas sem o modelo: 

Mentor offline. Ollama is running but the model `gemma4:cloud` is not installed.
Install it with `ollama pull gemma4:cloud`.

São problemas diferentes com ações diferentes. Colapsar os dois em "mentor indisponível" transfere para o jogador o trabalho de diagnosticar — e ele não tem como.

Nenhum método levanta exceção por rede

src/codequest/mentor/client.py

try:
    response = httpx.post(f"{self.host}/api/chat", json=payload, timeout=self.timeout_seconds)
except httpx.TimeoutException:
    return self._failure(MentorState.TIMED_OUT)
except httpx.HTTPError:
    return self._failure(MentorState.OFFLINE)

Uma exceção que sobe seria uma feature opcional derrubando o jogo. Retornar estado é o que torna "opcional" verdade em vez de intenção.

E nenhum retry

Uma escolha que merece defesa

O cliente tenta uma vez. Sem retry, sem backoff.

O raciocínio: uma máquina que já está com dificuldade de servir um modelo local não melhora sendo martelada, e o jogador está a uma tecla de perguntar de novo. Retry automático faz sentido quando a falha é transitória e o usuário não está presente — aqui ele está, olhando para a tela.

Num pipeline de agente sem ninguém olhando, a resposta seria a oposta. A decisão depende de quem está esperando.

[AI-ENG:graceful-degradation]

Para uma feature com LLM, falha é ramo normal, não excepcional. Modelo fora do ar, modelo lento, rate limit, resposta em formato errado, resposta vazia — tudo isso é terça-feira.

A prática: antes de escrever o caminho feliz, liste os estados de falha e decida o que o usuário vê em cada um. Se algum estado leva a "não sei o que mostrar", você encontrou um buraco no design da feature, não um detalhe de implementação.

7. Teoria 5 — Provar que é opcional

"O mentor é opcional" é fácil de dizer e fácil de quebrar sem perceber. Basta alguém adicionar um import conveniente no topo de um arquivo.

O padrão correto é importar dentro da função:

src/codequest/tui/widgets/mentor_chat.py

@work(thread=True, exclusive=True)
def _ask(self, question: str) -> None:
    """Talk to the model off the UI thread.

    The import lives here rather than at the top of the file: the mentor package is
    optional, and a module-scope import would make deleting it a crash on startup.
    """
    from codequest.mentor.client import MentorState, OllamaClient

E o teste que garante isso encontrou um bug no teste que já existia — o que é a parte interessante da história.

O bug no teste

O test_architecture.py usava ast.walk(), que percorre a árvore inteira, inclusive dentro de funções. Então ele sinalizou o import local — o padrão que a regra existe para exigir.

O docstring dizia "module scope" e o código não fazia isso. A correção foi separar duas perguntas que pareciam a mesma:

PerguntaEscopo que contaPor quê
Esta camada depende daquela? qualquer escopo Esconder uma dependência proibida dentro de uma função não faz dela uma não-dependência
Aquele pacote é opcional? só escopo de módulo Import dentro de função é exatamente como se torna um pacote opcional. Sinalizar seria proibir o padrão exigido

E a prova final não é um teste, é uma medição. Renomear a pasta e rodar a suíte inteira: 

$ mv src/codequest/mentor src/codequest/_mentor_disabled
$ pytest -q
# conjunto de falhas IDENTICO ao de antes

$ python -c "from codequest.tui.app import CodeQuestApp"
CodeQuestApp importa sem o mentor: OK

8. A ponte com AI Engineering

Esta fase inteira é AI Engineering, então a tabela é curta e a lista de princípios é longa.

No CodeQuestO princípio
Filtro do entrypoint na saídaGuardrail é código. Prompt é preferência
solution nunca montadaNão enviar vence filtrar depois, sempre
1.200 chars de contextoContexto é orçamento de atenção, não só de janela
Verdict no contextoOnde o usuário travou vale mais que o que ele digitou
Quatro estados de falha nomeadosFalha é ramo normal com UX própria
Uma tentativa, sem retryA política de retry depende de haver alguém esperando
Import dentro da funçãoOpcionalidade verificada, não prometida
31 testes, zero redeTestar integração de LLM sem chamar o modelo
A frase que resume o projeto inteiro

Desde a Fase 1, toda decisão importante deste repositório segue o mesmo padrão: tornar o resultado ruim estruturalmente impossível, em vez de filtrar para que não aconteça.

O jogador não forja o resultado porque não alcança o canal. O processo não trava o jogo porque é outro processo. O XP não é pago duas vezes porque o estado persistido decide. E o mentor não entrega a resposta porque nunca a recebeu.

Filtrar é o que sobra quando não dá para tornar impossível. É a segunda melhor opção, e reconhecer qual das duas você está usando é metade do trabalho.

9. Exercícios

1. Se o filtro de saída existe, por que se dar ao trabalho de não montar a solução no contexto?

Porque o filtro procura uma coisa específica: def <entrypoint>(. Um modelo que descreve a solução em prosa passa. Um modelo que a escreve com outro nome passa. Um modelo que a devolve em pseudocódigo passa.

Filtro pega o vazamento que você previu. Não enviar pega todos, inclusive os que você não pensou — e continua pegando depois de trocar de modelo, coisa que uma regex não garante.

2. O sistema tem 128k de janela e o contexto usa 1.200 caracteres. Por que não mandar a missão inteira, incluindo todos os testes?

Os testes escondidos são o motivo imediato: mandá-los transformaria a suíte oculta numa tabela de consulta, e a missão pararia de pegar respostas chumbadas.

Mas mesmo o que é inofensivo tem custo. Atenção é finita dentro da janela — informação irrelevante compete com a relevante. E num modelo local o prefill é a diferença entre dois e quinze segundos, que é a diferença entre usar e desistir.

"Cabe na janela" nunca foi o critério. O critério é "isto melhora a resposta?".

3. Você tem um agente de suporte que não pode prometer reembolso. Onde põe essa regra?

Nas três camadas, e é importante saber o que cada uma faz:

  1. Estrutura. O agente não tem ferramenta de emitir reembolso. Se ele não pode executar, prometer é no máximo constrangedor, não caro.
  2. Prompt. "Você não pode autorizar reembolsos; encaminhe para um humano." Reduz muito a frequência.
  3. Filtro de saída. Classificador ou padrão sobre a resposta; se promete reembolso, substitui por um encaminhamento.

A camada 1 é a única que é garantia. As outras duas reduzem probabilidade. E se o custo de errar for alto o bastante, existe a camada zero: um humano aprova antes de enviar.

4. Como você testa uma integração de LLM sem chamar o modelo — e o que esses testes não cobrem?

O que dá para testar sem rede, e este projeto testa: montagem de contexto (o que entra e o que fica de fora), o filtro de saída nos dois sentidos, e cada estado de falha do cliente, com o transporte HTTP mockado.

O que não dá: se o modelo é bom. Nenhum teste aqui diz se a resposta ajuda, se o tom está certo, ou se ele obedece ao system prompt na prática. Isso é trabalho de eval, com casos escritos à mão e julgamento — a mesma disciplina da Fase 3, aplicada a saída de modelo em vez de a conteúdo.

Confundir "meus testes passam" com "meu recurso de IA é bom" é o erro mais comum de quem vem de engenharia tradicional para AI Engineering. Testes cobrem a máquina em volta do modelo. A qualidade do modelo é medida, não testada.
