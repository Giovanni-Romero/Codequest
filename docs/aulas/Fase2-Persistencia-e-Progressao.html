1. O que foi construído

A Fase 1 sabia julgar código, mas esquecia tudo quando o processo terminava. A Fase 2 dá memória ao jogo: quatro tabelas em SQLite, uma camada de repositories que é o único lugar do projeto onde existe SQL, e um serviço que decide as regras de progressão.

O teste que resume a fase inteira roda em dois processos: 

$ codequest new-save giovanni
Created save #1 'giovanni' on the python track.

$ codequest play giovanni py-foundations-02 solucao.py
PASS  All 8 cases passed.
  +10 XP   total 10
  Unlocked island: foundations

$ codequest play giovanni py-foundations-02 solucao.py
PASS  All 8 cases passed.
  Already completed, no XP this time. Total 10

A terceira execução é o ponto. O código está certo, os oito casos passam, o veredito diz PASS — e o XP não se move. Essa distinção entre "deu certo" e "rendeu algo" é o assunto principal desta aula.

2. A analogia: o caderno da padaria

Uma padaria de bairro com caderneta de fiado. Duas colunas de informação convivem ali, e confundi-las é o erro clássico.

Tem o saldo de cada cliente: um número, atualizado, que responde "quanto ele deve agora". E tem o histórico: cada linha rabiscada, com data, respondendo "como chegamos nesse número".

O saldo é rápido de consultar e não conta história. O histórico conta história e é lento de somar. Você quer os dois — e no CodeQuest são as tabelas progress (o saldo) e attempt (o histórico).

Agora o detalhe que vira idempotência. Se o cliente paga a conta e o padeiro anota o pagamento duas vezes por distração, o saldo fica errado. A defesa não é "prestar mais atenção" — é a caderneta ter uma coluna que diz esta dívida já foi quitada, de modo que anotar de novo não muda nada.

3. Teoria 1 — Modelagem relacional

Quatro tabelas. Cada uma existe porque responde uma pergunta diferente.

Chave primária composta

progress tem PRIMARY KEY (profile_id, mission_id). Não é uma escolha estética: é uma regra de negócio codificada no schema. Um perfil tem no máximo uma linha de progresso por missão, e o banco recusa a segunda antes que qualquer código Python tenha chance de errar.

Regra útil: quando uma restrição é sobre a forma dos dados, coloque no schema. Quando é sobre política do produto, coloque no serviço. O limite de quatro saves é política — daí ele não estar aqui, e sim como exceção com mensagem amigável.

A pegadinha que quase todo mundo leva

SQLite desliga foreign keys por padrão

Por compatibilidade retroativa, e por conexão. Sem o pragma, cada cláusula REFERENCES do schema é decorativa: apagar um perfil deixaria linhas de progresso órfãs apontando para um id que não existe mais, em silêncio.

src/codequest/storage/db.py

connection = sqlite3.connect(path, isolation_level=None)
connection.row_factory = sqlite3.Row
connection.execute("PRAGMA foreign_keys = ON")
connection.execute("PRAGMA journal_mode = WAL")

E existe um teste que falha se alguém remover essa linha:

tests/unit/test_storage.py

def test_foreign_keys_are_enforced(db):
    """SQLite vem com foreign keys OFF. Sem o pragma, REFERENCES é decorativo."""
    with pytest.raises(sqlite3.IntegrityError):
        db.execute(
            "INSERT INTO progress (profile_id, mission_id, status) VALUES (?, ?, ?)",
            (999, "m1", "available"),
        )

Migrations: por que o save sobrevive a uma atualização

Uma migration é uma mudança de schema numerada e registrada. O banco guarda em que versão está; rodar as migrations de novo pula o que já foi aplicado. Sem isso, atualizar o jogo significaria recriar o banco, e o jogador perderia o save.

A regra que parece pedante e não é:

src/codequest/storage/db.py

#: Ordered schema migrations. Append only — never edit a shipped one, because a database
#: that already applied version 2 will never see the edit, and the two installs silently
#: diverge.

Editar uma migration já publicada cria dois bancos com o mesmo número de versão e estruturas diferentes. O bug aparece meses depois, numa máquina que não é a sua.

Um detalhe que só aparece rodando

Bug real desta fase

A primeira versão envolvia a migration num BEGIN explícito. Todos os testes de storage quebraram com cannot commit - no transaction is active.

Motivo: executescript do sqlite3 faz um commit implícito antes de rodar o script. O BEGIN em volta da chamada já tinha sido descartado quando o script começou. A correção foi mover BEGIN e COMMIT para dentro do script.

Vale a lição geral: APIs de banco têm comportamento transacional implícito, e ele raramente é o que a leitura casual sugere.

4. Teoria 2 — Repository: onde o SQL mora

O padrão repository diz: todo acesso a dados de uma entidade fica numa classe, que recebe e devolve objetos de domínio. Quem chama nunca escreve SQL.

CamadaSabeNão sabe
models/a forma dos dadosque existe um banco
storage/SQL, tabelas, transaçõesas regras do jogo
services/as regras do jogoSQL

O benefício imediato não é "código limpo", que é vago. É concreto: quando o XP parar de ser contado direito, existe exatamente um arquivo onde a escrita acontece, e você não precisa procurar um UPDATE perdido dentro de um widget.

A escolha de somar no banco

src/codequest/storage/repositories.py

def add_xp(self, profile_id: int, amount: int) -> None:
    """Increment total XP.

    Written as ``total_xp = total_xp + ?`` rather than read-modify-write in Python:
    the addition happens inside the database, so two concurrent awards cannot both
    read the old value and one of them overwrite the other.
    """
    self.connection.execute(
        "UPDATE profile SET total_xp = total_xp + ?, last_played_at = ? WHERE id = ?",
        (amount, _now(), profile_id),
    )

A alternativa — ler o total em Python, somar, gravar de volta — funciona até dois caminhos fazerem isso ao mesmo tempo. Aí ambos leem 10, ambos gravam 20, e um dos dois ganhos desaparece. Chama-se lost update. Fazer a aritmética dentro do banco elimina a janela em vez de torcer para ela não acontecer.

É o mesmo raciocínio da Fase 1, aliás: tornar o resultado ruim estruturalmente impossível, em vez de filtrar para que não aconteça.

5. Teoria 3 — Injeção, e por que parametrizar vence escapar

Injeção de SQL acontece quando texto que deveria ser dado é lido como instrução. O exemplo canônico, escrito da forma errada: 

# NUNCA FAÇA ISSO
cursor.execute(f"SELECT * FROM profile WHERE name = '{name}'")

Com name = "Robert'); DROP TABLE profile;--", o banco recebe:

SELECT * FROM profile WHERE name = 'Robert'); DROP TABLE profile;--'

A aspa fechou a string, o ponto e vírgula terminou o comando, e o resto virou um segundo comando. A forma certa:

src/codequest/storage/repositories.py

row = self.connection.execute(
    "SELECT * FROM profile WHERE name = ?", (name,)
).fetchone()

A diferença não é cosmética. Com ?, a string do SQL é compilada num plano de execução antes do valor chegar. O valor é depositado num espaço já reservado e não pode mais alterar a estrutura do comando — a possibilidade some, não é filtrada.

Existe um teste que prova isso com o payload clássico:

tests/unit/test_storage.py

def test_a_profile_name_that_looks_like_sql_is_stored_as_text(db, profiles):
    hostile = "Robert'); DROP TABLE profile;--"

    profiles.create(hostile, "python")

    assert profiles.get_by_name(hostile).name == hostile
    assert db.execute("SELECT COUNT(*) AS n FROM profile").fetchone()["n"] == 1

O nome vira um nome bobo. A tabela continua lá. Ninguém precisou lembrar de escapar nada.

A única interpolação do projeto

Existe exatamente uma, em db.py, porque executescript não aceita parâmetros. Ela é segura por razão estrutural e não por otimismo: o valor é um int de uma constante declarada no mesmo arquivo, e int() transforma qualquer outra coisa em TypeError antes de chegar ao banco.

Está comentada no ponto de uso justamente para nunca ser lida como permissão para a próxima. Exceção documentada é diferente de regra frouxa.

[AI-ENG:sql-injection]

A classe de bug é texto não confiável numa posição onde pode ser lido como instrução. Em AI Engineering ela reaparece o tempo todo, com outras roupas:

  • documento recuperado por RAG virando parte do prompt
  • argumento de tool call virando parte de um comando de shell
  • saída de modelo virando parte de uma query
  • memória de agente escrita numa sessão e lida em outra

A pergunta que transfere: este texto pode ser interpretado como instrução onde ele vai parar? Se pode, você precisa de uma fronteira estrutural — parâmetro, schema tipado, canal separado — e não de um filtro.

6. Teoria 4 — Transação

Conceder XP toca três tabelas: registra a tentativa em attempt, atualiza progress, soma em profile, e às vezes insere em unlocked_island. Uma queda no meio disso deixaria o jogador com uma missão marcada como completa e sem o XP, ou o contrário.

Uma transação torna o conjunto atômico: ou tudo acontece, ou nada acontece. Não existe meio.

src/codequest/storage/db.py

@contextmanager
def transaction(connection: sqlite3.Connection) -> Iterator[sqlite3.Connection]:
    connection.execute("BEGIN")
    try:
        yield connection
    except BaseException:
        connection.execute("ROLLBACK")
        raise
    else:
        connection.execute("COMMIT")

Note except BaseException e não except Exception. Um KeyboardInterrupt — o jogador apertando Ctrl+C no meio de um save — não herda de Exception. Com o except mais estreito, o Ctrl+C passaria direto sem fazer rollback e deixaria a escrita pela metade.

7. Teoria 5 — Idempotência

Aqui está o conceito mais valioso da fase.

Uma operação é idempotente quando executá-la várias vezes tem o mesmo efeito que executá-la uma vez. A analogia direta: apertar o botão do elevador. O primeiro toque chama; do segundo ao décimo não acontece nada de novo. O elevador não vem duas vezes.

O oposto é "cobrar o cartão". Repetir cobra de novo, e isso é um problema real.

Como o CodeQuest garante

src/codequest/services/progress_service.py

with transaction(self.connection):
    existing = self.progress.get(profile.id, mission.id)
    already_completed = existing is not None and existing.is_completed

    # A decisão, numa linha: pague apenas na primeira vez.
    xp_to_award = mission.xp if (verdict.passed and not already_completed) else 0

Repare em onde a decisão é tomada. Não numa flag passada pelo chamador, não numa variável de sessão, não num "cuidado para não chamar duas vezes" no comentário. Ela é derivada de estado que está no banco, dentro da transação que vai escrever.

Essa é a diferença entre idempotência de verdade e disciplina:

AbordagemSobrevive aQuebra em
"não chame duas vezes"nadaretry, duplo clique, crash e replay
flag em memóriachamadas na mesma sessãoreinício do processo
estado persistidotudo acima—

A defesa em profundidade

O serviço decide, e o repositório também se protege, com um upsert que nunca regride:

src/codequest/storage/repositories.py

ON CONFLICT (profile_id, mission_id) DO UPDATE SET
    attempts     = attempts + 1,
    best_xp      = MAX(best_xp, excluded.best_xp),
    status       = CASE
                       WHEN progress.status = 'completed' THEN 'completed'
                       ELSE excluded.status
                   END,
    completed_at = COALESCE(progress.completed_at, excluded.completed_at)

MAX impede o XP de cair. O CASE impede uma missão completa de voltar a "tentada" quando o jogador erra numa releitura futura. COALESCE preserva a data original da conquista. Cada cláusula existe para que escrever de novo não desfaça nada.

E o teste que fecha o assunto:

tests/unit/test_progress_service.py

def test_replaying_ten_times_still_pays_once(service):
    """Repetição precisa ser entediante, não cara. Esta é a propriedade de retry-safety."""
    profile = service.create_profile("giovanni", "python")

    for _ in range(10):
        profile = service.record_attempt(profile, MISSION, "code", PASSED).profile

    assert profile.total_xp == 10
[AI-ENG:idempotency]

Todo pipeline de agente sério faz retry. A rede cai, o modelo retorna 529, um passo dá timeout e o orquestrador tenta de novo. Se um passo com efeito colateral não for idempotente, o retry cobra o cartão duas vezes, manda o email duas vezes, cria o ticket duas vezes.

O padrão da indústria é chave de idempotência: o chamador gera um id para a operação, o executor guarda o resultado indexado por esse id, e uma repetição devolve o resultado guardado em vez de executar de novo. É a mesma ideia deste progress — o estado persistido decide, não a boa vontade de quem chama.

Se você projetar cada ferramenta de agente para ser idempotente, o retry deixa de ser perigoso e o sistema fica simples. Se não, você vai passar o resto do projeto escrevendo lógica de compensação.

A honestidade na interface

Um detalhe pequeno que revela a disciplina. O AwardResult separa dois números que parecem o mesmo:

src/codequest/services/progress_service.py

``xp_awarded`` is what the player *gained now*, which is zero on a replay even
though the verdict says the mission passed. The UI needs the difference: showing
"+10 XP" on a mission that granted nothing is a lie the player will notice.

O veredito carrega o valor da missão; o award carrega o que foi de fato concedido. Colapsar os dois num campo só produziria uma interface que mente — e o jogador percebe na hora que o total não sobe.

8. A ponte com AI Engineering

No CodeQuestEm AI Engineering

Limite de saves é regra de serviçoPolítica no serviço, invariante no schema
A tabela attempt merece um parágrafo

Ela guarda cada submissão com o código completo e o veredito. Do ponto de vista do jogo, é para o jogador reler o que escreveu semanas atrás.

Do ponto de vista de AI Engineering, é um trace. É exatamente o que você quer de um agente em produção: a entrada, a saída, o resultado, o timestamp — de cada passo, gravados de forma append-only. Sem trace, depurar um agente é adivinhação; progress te diz onde ele está, attempt te diz como chegou lá.

9. Exercícios

1. Por que o limite de quatro saves é uma exceção do serviço e não um CHECK no schema?

Porque é política de produto, não invariante de dados. Uma constraint de banco produziria IntegrityError; o serviço produz "você já tem 4 saves. Apague um antes de criar outro."

E porque política muda. Se o jogo passar a oferecer seis slots, mexer numa constante é diferente de escrever uma migration. A regra: forma dos dados vai para o schema, política vai para o serviço.

2. Um jogador dá duplo clique em "enviar" e a mesma solução é submetida duas vezes ao mesmo tempo. O que acontece?

A segunda tentativa é registrada em attempt (correto — ela realmente aconteceu), progress.attempts vai a 2 (também correto), e o XP é pago uma vez só. A transação serializa as duas escritas, e a segunda enxerga status = 'completed' gravado pela primeira.

Note que a resposta depende da leitura estar dentro da mesma transação da escrita. Ler antes de abrir a transação abriria a janela de volta.

3. Por que except BaseException no gerenciador de transação, e não except Exception?

Porque KeyboardInterrupt e SystemExit herdam de BaseException, não de Exception. Um Ctrl+C no meio de um save escaparia do except mais estreito, o ROLLBACK nunca rodaria, e a escrita ficaria pela metade.

Regra prática: except Exception para tratar erro; BaseException para limpeza que precisa acontecer de qualquer jeito. Ou, melhor ainda, um finally.

4. Você está construindo um agente que envia emails. Como aplica o que esta fase ensina?
  1. Chave de idempotência. Derive um id determinístico da intenção (destinatário + assunto + hash do corpo, ou o id da tarefa que originou o envio). Grave antes de enviar.
  2. Decida por estado persistido. Antes de chamar a API, consulte se aquela chave já foi enviada. Dentro da mesma transação, como no record_attempt.
  3. Separe estado e trace. Uma tabela "email enviado" (o saldo) e uma "tentativas de envio" com resposta da API e timestamp (o histórico). Quando algo der errado, você vai precisar das duas.
  4. Cuidado com a fronteira dado/instrução. Se o corpo do email vem de conteúdo recuperado, ele é texto não confiável. Não o deixe influenciar para quem o email vai.

O ponto difícil é o item 1: enviar e depois marcar deixa uma janela em que o crash causa envio duplo. Marcar e depois enviar deixa uma janela em que o crash causa email perdido. Não existe solução perfeita sem transação distribuída — você escolhe qual falha prefere, e para email quase sempre se prefere perder a duplicar.
