1. O que foi construído

A ilha Foundations, completa: dez missões cobrindo seis conceitos, do primeiro valor guardado numa variável até um relatório que combina todos eles. Mais o desconto de XP por dica, que fechou uma promessa que o README fazia e o código não cumpria.

E, o mais importante, a suíte que prova que tudo isso funciona: 

$ codequest check
[PASS] py-foundations-01  The ship's stores
[PASS] py-foundations-02  Is that a number?
...
[PASS] py-foundations-10  The log at end of watch

10/10 missions self-consistent

Sessenta e seis asserções, geradas automaticamente a partir dos arquivos. Cada uma prova que a solução declarada numa missão passa nos próprios testes visíveis e escondidos, e obedece às restrições que a própria missão declara.

2. A analogia: o manual de treinamento

Uma companhia de navegação treina timoneiros. Duas empresas concorrentes fazem isso de formas opostas.

Na primeira, o treinamento está na cabeça do instrutor. Ele sabe a ordem, sabe o que costuma confundir, improvisa exemplos. Funciona bem — enquanto for ele. Quando adoece, ninguém consegue substituí-lo, e ninguém consegue revisar o que ele ensina porque não está escrito em lugar nenhum.

Na segunda, o treinamento é um manual. Ordem numerada, pré-requisito de cada lição, erros comuns listados, e um exercício de verificação por lição. Qualquer instrutor consegue dar a aula. Qualquer pessoa consegue apontar que a lição 7 depende de algo que só aparece na lição 9.

O CodeQuest é a segunda empresa. O currículo é um documento, as missões são arquivos, e a coerência entre os dois é verificada por máquina. É a diferença entre conhecimento que mora numa pessoa e conhecimento que mora num artefato.

3. Teoria 1 — Conteúdo como dado, não como código

A decisão mais antiga do projeto, tomada antes de existir uma linha de motor: uma missão é um arquivo YAML, nunca um módulo Python.

content/tracks/python/locales/en/islands/01-foundations/missions/04-grade-or-fail.yaml

id: py-foundations-04
title: The navigator's exam
difficulty: elementary
xp: 10

concepts: [conditionals, basic-types]

teaching:
  analogy: |
    A customs officer at the gangway asks questions in a fixed order...
  key_points:
    - Only one branch of an if / elif chain runs. The first true condition wins.

constraints:
  forbidden_builtins: []

tests:
  visible:
    - args: [95]
      expect: "gold"
  hidden:
    - args: [90]
      expect: "gold"
    - args: [89]
      expect: "silver"

Escolher dado em vez de código compra quatro coisas concretas:

PropriedadePor que importa aqui
Não executaUm arquivo de conteúdo não pode ter um bug de runtime, não pode entrar em loop, não pode abrir um socket
ValidávelUm schema descreve o que é válido. Código só é validável rodando
Diff legívelMudar uma dica é uma linha no diff. Numa classe Python seria ruído entre chaves e indentação
ContribuívelAlguém que sabe ensinar loops pode escrever uma missão sem saber nada do motor

A regra correspondente está no CLAUDE.md §3 e é verificada por teste: content/ não pode conter nenhum .py. Não é higiene — é o que impede o conteúdo de virar um vetor de execução.

O custo, dito por inteiro

Dado precisa de uma camada de validação que código não precisaria. Um erro de digitação num arquivo Python o interpretador pega; num YAML, ninguém pega — a não ser que você escreva quem pega.

O loader.py e o test_all_missions.py existem por causa dessa escolha. É um custo real, pago de propósito, e a próxima seção é sobre ele.

4. Teoria 2 — Validar dado declarativo

Um arquivo de missão parece o contrato e silenciosamente pode não ser. O loader tem duas regras que definem como ele lida com isso.

Faça o parse, depois valide

Nunca as duas coisas ao mesmo tempo. Validar durante o parse produz mensagens sobre a posição do parser — "erro na linha 47, coluna 12" — quando o que o autor precisa ouvir é "falta o campo solution".

Reporte tudo de uma vez

src/codequest/engine/loader.py

def _validate_mission(raw: Any) -> list[str]:
    """Return every schema problem found in ``raw``. An empty list means valid.

    # [AI-ENG:schema-validation] Declarative data from outside the program is exactly
    # the shape of an LLM's structured output: it *looks* like the contract and
    # silently is not. Validating the whole document and reporting all violations at
    # once is what turns a vague "the model returned garbage" into a fixable list.
    """
    problems: list[str] = []
    ...
    return problems

Repare que a função devolve uma lista e não levanta na primeira falha. Um validador que para no primeiro erro transforma um arquivo com cinco problemas em cinco ciclos de editar-rodar-editar.

[AI-ENG:schema-validation]

Troque "arquivo YAML escrito à mão" por "JSON devolvido por um modelo" e nada mais muda. É a mesma classe de problema: dado externo que se parece com o contrato.

A prática que transfere é a de coletar todas as violações. Quando um modelo devolve estrutura errada, você quer a lista completa — para consertar o prompt de uma vez, ou para devolver ao modelo um erro que ele consiga corrigir num único passo. "O modelo retornou lixo" não é acionável; "faltam os campos x e y, e z veio como string em vez de número" é.

5. Teoria 3 — Design de currículo é design de eval

Esta é a seção que justifica o título da aula.

O curriculum-designer impõe três regras ao ordenar conceitos, e elas são as mesmas regras de quem monta um conjunto de avaliação sério:

Regra do currículoA mesma regra num eval
Nunca dois conceitos novos na mesma missão Cada caso isola uma capacidade. Se o caso testa raciocínio e formatação ao mesmo tempo, a falha não diz qual dos dois quebrou
Um conceito só depende do que veio antes Não avalie uma capacidade cujo pré-requisito você não verificou. Falhar em aritmética não é falhar em raciocínio
Todo conceito é reusado pelo menos duas vezes Uma capacidade medida uma vez é ruído. Medir de novo em contexto diferente separa acerto de sorte

6. Teoria 4 — Testes escondidos são teste adversarial

Toda missão tem dois grupos de teste. Os visíveis ensinam a forma do problema. Os escondidos existem para pegar quem passou sem aprender.

A regra que os governa, do docs/mission-schema.md:

Regra

Se devolver uma constante passa em todos os testes visíveis, acrescente testes escondidos até não passar.

Repare no que isso é: você assume o papel de alguém tentando burlar a sua própria avaliação, e projeta contra essa pessoa. Alguns exemplos reais desta ilha:

MissãoO que o teste escondido pega
2 — Is that a number?True e False. Quem checou só isinstance(v, int) passa nos visíveis e falha aqui, porque em Python um bool é um int
4 — The navigator's examOs valores exatos de fronteira: 90, 89, 70, 69, 50, 49. Quem escreveu > onde precisava de >= só descobre aqui
7 — The longest nameUm empate. Decide se a implementação guarda o primeiro ou o último, que era uma escolha que o brief exigia fazer de propósito
10 — The log at end of watchUm log só com leituras negativas. Pega o acumulador de "maior até agora" iniciado em zero — que parece inofensivo e vence contra qualquer valor real negativo

E há uma segunda camada, que é o que impede a missão de ensinar a coisa errada:

content/.../05-count-the-vowels.yaml

constraints:
  forbidden_builtins: [count, sum]

A missão ensina a percorrer texto contando. text.count("a") resolve sem ensinar nada. Sem essa linha, a missão existe mas não funciona.

[AI-ENG:failure-taxonomy] · adversarial evaluation

Um conjunto de eval que só testa o caminho feliz mede se o modelo funciona quando tudo dá certo, o que já se sabia. O valor está nos casos construídos para quebrar: entrada ambígua, contexto contraditório, a pergunta cuja resposta honesta é "não sei", o prompt que tenta redirecionar a instrução.

E o paralelo do forbidden_builtins é direto: se o seu eval pode ser vencido por decorar o formato da resposta em vez de resolver a tarefa, ele mede memorização. A pergunta a fazer sempre é "qual é o atalho barato aqui, e o meu conjunto o rejeita?"

7. Os dois erros desta fase, contados inteiros

Os dois foram meus, os dois foram pegos antes de commitar, e os dois são o mesmo tipo de erro: uma afirmação que parecia óbvia demais para verificar.

Erro 1: a missão de exemplo desobedecia ao próprio currículo

O repositório já vinha com 02-sum-list.yaml como exemplo de referência. Ela declara: 

order: 2
concepts:
  - accumulator-pattern
  - for-loop

Dois conceitos novos no mesmo arquivo, e na posição 2 — antes de variáveis, tipos ou condicionais existirem. A regra que ela quebra é a primeira do curriculum-designer, e é a regra de que todo o resto do currículo depende.

Ela foi para a posição 6, depois que for-loop é ensinado na 5. Custou atualizar seis referências em arquivos de teste. Barato agora; mais caro a cada missão nova que fosse adicionada antes de alguém perceber.

Erro 2: eu escrevi a missão 2 usando algo que só aparece na missão 4

Este é o mais instrutivo, porque aconteceu depois de eu ter desenhado a matriz que existe justamente para impedi-lo.

A missão 2 ensina tipos. A minha primeira versão dela era assim: 

def type_name(value):
    if isinstance(value, bool):
        return "bool"
    elif isinstance(value, int):
        return "int"
    ...

Solução natural, boa missão — e if/elif só é ensinado na missão 4. O jogador chegaria na missão 2 e precisaria de uma construção que o jogo ainda não mostrou.

A correção foi reformular a tarefa para caber no que já existe:

content/.../02-type-detective.yaml

def is_whole_number(value):
    return isinstance(value, int) and not isinstance(value, bool)

Expressão booleana, sem ramificação. A armadilha valiosa — isinstance(True, int) ser verdadeiro — sobreviveu inteira, que era o ponto da missão.

Por que isso escapou

A matriz registra os conceitos que uma missão declara. Não registra os que ela usa sem declarar. Eu escrevi concepts: [basic-types, variables], o que era verdade, e a solução mesmo assim precisava de condicionais.

A defesa que ficou é uma nota explícita no syllabus dizendo que missões 2 e 3 não podem usar if. Uma nota é mais fraca que um teste, e é o que dá para fazer hoje — verificar automaticamente exigiria analisar a AST de cada solução contra o conjunto de construções já ensinadas. Vale registrar como dívida honesta em vez de fingir que a matriz cobre.

8. A ponte com AI Engineering

No CodeQuestEm AI Engineering
Conteúdo é YAML, nunca códigoPrompt e configuração como dado versionado, não como string no meio da lógica
Loader valida e reporta tudo de uma vezValidação de structured output com lista completa de violações
Um conceito novo por missãoUm caso de eval isola uma capacidade
Conceito reusado duas vezesMedir a mesma capacidade em contextos diferentes separa acerto de sorte
Testes escondidosCasos adversariais; eval que só mede caminho feliz não mede nada
forbidden_builtinsFechar o atalho que passa no eval sem resolver a tarefa
codequest check no CIRodar o eval a cada mudança, não só antes de lançar
A ideia que amarra

O test_all_missions.py não testa o motor. Ele testa o conteúdo, usando o motor como instrumento de medida.

Essa inversão é o que um harness de eval é. Você não está verificando se o seu código de avaliação funciona; está usando código que funciona para medir a qualidade de outra coisa. Reconhecer de qual lado você está muda o que você escreve: quando o alvo é o conteúdo, um caso que falha é um achado, não um bug a silenciar.

9. Exercícios

1. Por que content/ não pode conter nenhum .py, se o projeto já executa código do jogador num sandbox?

São confianças diferentes. O código do jogador é executado num subprocess matável, com timeout, e o jogador escolheu rodá-lo. Um arquivo de conteúdo é importado pelo jogo, no processo do jogo, sem sandbox nenhum.

E há a razão de produto: o dia em que missões vierem de pull request de outras pessoas, "conteúdo é dado" é a diferença entre revisar YAML e revisar código que vai rodar na máquina de quem instalar.

2. A missão 5 proíbe count e sum. O jogador escreve text.count("a"). Como o guard pega isso, se count é método de string e não builtin?

O _SubmissionVisitor tem um visit_Attribute que compara node.attr com a lista de proibidos. text.count é um nó Attribute cujo attr é "count", então bate.

Detalhe que vale notar: essa checagem não passa pela isenção de nomes ligados pelo jogador. Uma variável chamada count é isentada; um atributo chamado count não. As duas decisões estão certas por motivos diferentes.

3. Você tem um eval de 200 casos e o modelo acerta 94%. Que três perguntas fazer antes de comemorar?
  1. Os 200 casos isolam capacidades diferentes, ou 150 medem a mesma coisa? Um conjunto desbalanceado transforma uma capacidade em 75% da nota.
  2. Existe atalho barato que passa sem resolver? Se responder sempre o formato mais comum já dá 60%, o número mede formato e não tarefa. É a versão eval do forbidden_builtins.
  3. Os 6% que falham são todos do mesmo tipo? Sem taxonomia de falha, 94% é um número. Com taxonomia, você descobre que 5 dos 6 pontos são um único modo de erro consertável.

Bônus, o mais desconfortável: quantos dos 200 casos você escreveu tentando quebrar o modelo, e quantos escreveu esperando que ele passasse? A proporção prevê o quanto o número vai se sustentar em produção.

4. O erro 2 desta fase — usar uma construção não ensinada — passou pela matriz de conceitos. Como você o pegaria automaticamente?

Faria o parse da solution de cada missão com ast e coletaria os tipos de nó usados: ast.If, ast.For, ast.While, e assim por diante. Depois mapearia cada tipo de nó para o conceito que o ensina, e afirmaria que toda construção usada foi introduzida numa missão de ordem menor ou igual.

O motor para isso já existe — é o mesmo NodeVisitor do guard.py, apontado para a solução em vez de para o código do jogador.

Não foi construído ainda, e essa é a resposta honesta: a nota no syllabus é uma salvaguarda mais fraca que um teste, e está registrada como tal. Reconhecer a diferença entre "documentei" e "verifiquei" é metade do valor da lição.
