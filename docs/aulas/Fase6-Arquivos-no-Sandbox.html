Arquivos no Sandbox

Umas quarenta linhas de código, e nelas mora uma das classes de vulnerabilidade mais antigas e mais teimosas da computação. Um nome de arquivo que vem de fora e vira caminho de escrita. A lição não é "valide a entrada" — é rejeitar não é o mesmo que limpar.

1. O que foi construído

A Ilha 7 do currículo — Files and Data — ensina a abrir, ler e escrever arquivos. Só que o sandbox do CodeQuest, até esta fase, escrevia exatamente dois arquivos no diretório temporário: o código do jogador e o harness. Uma missão que dissesse "leia cargo.csv" não teria nada para o jogador abrir.

Então nasceu um campo novo no schema de missão:

content/tracks/python/locales/en/islands/07-files-and-data/missions/01-the-logbook-page.yaml

files:
  cargo.csv: |
    port,weight
    lisbon,10
    porto,4

Um mapa de nome de arquivo para conteúdo em texto. O loader valida, o runner planta no diretório do sandbox antes de rodar, e o jogador faz open("cargo.csv") sem precisar saber onde está. Três arquivos de produção mudaram, mais o schema documentado e sete testes novos.

O detalhe que faz a fase existir

Esse YAML é a parte do repositório que um não-programador é convidado a editar. É dado, não código, e essa é a promessa. Um nome de arquivo vindo dali que vire caminho de escrita transforma "editar conteúdo" em "escrever qualquer arquivo da máquina". A promessa se quebra em silêncio.

2. A analogia: o porteiro e a lista

Um prédio contrata dois porteiros diferentes. Os dois têm o mesmo objetivo: só moradores entram.

O primeiro porteiro é do tipo prestativo. Alguém chega dizendo "sou o João do 402, mas esqueci o crachá" e ele pensa: bom, existe um João no 402, o rosto é parecido, deixa entrar. Alguém chega com um crachá de outro prédio e ele apaga a logo errada com corretivo e deixa entrar. Ele está sempre consertando a credencial até ela virar aceitável.

O segundo porteiro tem uma lista e um leitor de crachá. Crachá válido na lista: entra. Qualquer outra coisa — crachá vencido, crachá quase certo, crachá que daria pra consertar — não entra. Ele não negocia, não interpreta e não conserta.

O primeiro porteiro parece mais gentil e é infinitamente mais fácil de burlar, porque o atacante só precisa achar uma forma de credencial que ele conserte errado. O segundo é chato e é o único que funciona. A validação de nome de arquivo desta fase é o segundo porteiro.

3. Teoria 1 — Path traversal, formalmente

Path traversal (ou directory traversal) é a vulnerabilidade em que um valor controlado por quem está de fora é usado para montar um caminho no sistema de arquivos, e esse valor contém elementos de navegação que fazem o caminho final sair do diretório onde deveria ficar.

O elemento clássico é .., que em praticamente todo sistema de arquivos significa "o diretório acima". Junte isso a um join ingênuo: 

workdir = Path("/tmp/codequest-abc123")
name = "../../../../home/giovanni/.ssh/authorized_keys"   # veio do YAML

(workdir / name).write_text(conteudo)
# resolve para /home/giovanni/.ssh/authorized_keys

Repare que Path.__truediv__ fez exatamente o que foi pedido. Não há bug no pathlib. O bug é ter tratado um nome não confiável como se fosse um nome.

Em Python há uma segunda armadilha, e ela é pior porque não envolve .. nenhum: 

>>> from pathlib import Path
>>> Path("/tmp/sandbox") / "/etc/passwd"
PosixPath('/etc/passwd')

Um segmento absoluto descarta tudo o que veio antes. O mesmo vale para Path("C:/sandbox") / "D:/dados.txt" no Windows. Quem confia no join para "manter dentro" está confiando numa garantia que a biblioteca nunca ofereceu.

Formas que o mesmo ataque assume

EntradaPor que passa por um filtro ingênuo
../../etc/passwdO caso óbvio, o único que todo mundo lembra de bloquear
..\..\Windows\evil.txtSeparador do Windows. Um filtro que só olha / aprova
/etc/passwdNão tem ... É absoluto, e o join descarta o prefixo
C:\Windows\evil.txtLetra de drive. Absoluto no Windows sem começar com separador
%2e%2e%2fURL-encoded. Vira ../ depois de um decode que acontece adiante
....//Só é perigoso depois de um saneamento mal feito. Veja a seção 4
Sendo honesto sobre o CodeQuest

Neste projeto o atacante realista não é um invasor remoto — é um erro de digitação de quem escreve conteúdo, ou um YAML copiado de algum lugar sem ser lido. O jogo roda local e single-player. A validação está aqui porque a classe do bug é a mesma de um servidor, e porque um dia essa mesma reflexão vai valer num lugar onde o atacante é de verdade.

4. Teoria 2 — Por que sanear perde e rejeitar ganha

A tentação, ao ver ../ num nome, é tirá-lo: 

def limpar(nome):
    return nome.replace("..", "")     # NÃO FAÇA ISSO

Agora rode "....//etc/passwd" por essa função. Ela encontra o .. das posições 0-1 e remove. Encontra o .. das posições 2-3 e remove. Sobra "//etc/passwd". E ela mesma construiu a string perigosa a partir de uma string que não era exatamente perigosa antes.

A diferença profunda entre as duas abordagens é qual pergunta você está tentando responder:

SanearRejeitar
Pergunta "Como transformo isto em algo seguro?" "Isto é exatamente o que eu esperava?"
Conjunto Infinito — todas as entradas erradas possíveis Finito — a forma única que você aceita
Erro custa Uma brecha silenciosa em produção Uma mensagem de erro para o autor do conteúdo
Testável Só contra os ataques que você imaginou Contra a definição inteira do que é válido

É o mesmo argumento de blocklist-vs-allowlist que apareceu no guard da Fase 1, aplicado a caminhos em vez de a builtins. Enumerar o proibido perde de quem escolhe de um conjunto infinito. Enumerar o permitido inverte a assimetria.

5. Teoria 3 — Estado que sobrevive entre execuções

A segunda decisão da fase não é de segurança, é de correção — e ela só existe porque alguém foi ler como o engine realmente roda os casos de teste.

O GameSession chama prepare() uma vez por submissão e execute() uma vez por caso de teste. Cada caso ganha um processo novo — isso já estava garantido desde a Fase 1 — mas todos os processos compartilham o mesmo diretório.

Numa missão que ensina a escrever em arquivo, isso é veneno: 

Caso 1: append "x" em log.txt  →  log.txt = "seed:x"   ✓ passa
Caso 2: append "x" em log.txt  →  log.txt = "seed:xx"  ✗ falha

O jogador escreveu código correto e o caso 2 reprovou por causa do lixo do caso 1. Pior: o resultado passa a depender da ordem dos casos, que é a assinatura de um teste não determinístico.

Havia duas saídas. A primeira: escrever as dez missões da ilha de modo que cada caso use um arquivo diferente. A segunda: replantar os arquivos declarados antes de cada caso. A segunda ganhou por um motivo que não é técnico —

quem escreve missão não deveria precisar saber que o diretório é reutilizado. Se a correção do engine mora na cabeça do autor de conteúdo, ela vai ser esquecida na décima primeira missão.

O princípio

Isolamento que depende de disciplina não é isolamento. Ou o sistema garante o estado inicial, ou ele vai variar. Vale para caso de teste, para sessão de agente e para qualquer coisa que rode "de novo, do zero".

6. O código, anotado

6.1 A validação, no loader

src/codequest/engine/loader.py

_RESERVED_SANDBOX_NAMES = frozenset({"submission.py", "harness.py", "request.json", "result.json"})


def _rejects_as_filename(name: str) -> str | None:
    """Return why ``name`` is unusable as a sandbox filename, or None when it is fine.

    # [AI-ENG:path-traversal] A name that arrives as declarative data and then becomes a
    # write path is the same bug as an agent taking the filename straight out of the
    # model's tool call. The defence is to *reject* the whole name when it is not a plain
    # single segment — never to clean it up. Sanitising invites the arms race: stripping
    # ``"../"`` from ``"....//....//etc"`` *produces* ``"../../etc"``. Rejecting ends it.
    """
    if not isinstance(name, str) or not name:
        return "must be a non-empty string"
    # Both separators are checked on every platform, so a Linux CI run cannot green-light
    # a name that would escape the sandbox once a player opens the game on Windows.
    if "/" in name or "\\" in name:
        return "must be a plain filename, with no directory separator"
    if ":" in name:
        return "must not contain a drive letter or stream marker"
    if name.startswith("."):
        return "must not start with a dot"
    if name in _RESERVED_SANDBOX_NAMES:
        return f"is reserved by the runner ({', '.join(sorted(_RESERVED_SANDBOX_NAMES))})"
    return None

Cinco pontos que valem parar:

  • A função devolve o motivo, não um booleano. O loader acumula problemas e mostra todos de uma vez — a regra número 2 do módulo desde a Fase 1. Um bool obrigaria o chamador a inventar a mensagem, e ele não sabe qual regra falhou.
  • Os dois separadores são checados nos dois sistemas. O CI roda Linux, o Giovanni joga no Windows. Um filtro que só olhasse / ficaria verde no CI e traria a brecha junto no instalador.
  • ":" cobre duas coisas. Letra de drive (C:\...) e alternate data stream do NTFS (arquivo.txt:oculto), que é um jeito de escrever dados invisíveis num arquivo aparentemente inocente.
  • startswith(".") resolve três casos com uma linha: ".", ".." e arquivos ocultos. Nenhuma missão precisa começar um nome com ponto, então o custo de proibir é zero.
  • Nomes reservados. Não é segurança, é diagnóstico. Uma missão que declarasse submission.py sobrescreveria o código do jogador e ele veria um erro impossível de entender.

6.2 O plantio, no runner

src/codequest/engine/runners/python.py

def _plant_files(workdir: Path, files: tuple[tuple[str, str], ...]) -> None:
    """Write the mission's declared data files into the sandbox, overwriting freely.

    Names arrive already validated by the loader, which rejects anything that is not a
    plain filename. This function deliberately does no validation of its own and no
    joining cleverness: ``workdir / name`` is safe *because* of that upstream rule, and
    a second, weaker check here would only invite someone to relax the first one.
    """
    for name, content in files:
        (workdir / name).write_text(content, encoding="utf-8")
Uma decisão discutível, dita como decisão

Defesa em profundidade diria para validar de novo aqui. O argumento contrário, que venceu: duas validações em lugares diferentes viram uma validação e meia. A segunda é sempre a mais fraca, e a existência dela é o que convence alguém a afrouxar a primeira ("relaxa, o runner confere"). Uma fronteira, um dono, uma regra — e o docstring diz alto de quem é. Isso é convenção, não lei; num sistema com fronteira de rede no meio a resposta seria a oposta.

6.3 O replantio, antes de cada caso

src/codequest/engine/runners/python.py — dentro de execute()

        # The workdir outlives a single case, so a submission that wrote to a declared
        # file - which is the whole point of the Files island - would hand the next case
        # its leftovers. Re-planting makes every case start from the mission's own data,
        # and means a mission author never has to know the workdir is shared.
        try:
            _plant_files(workdir, prepared.files)
        except OSError as exc:
            raise RunnerError(f"cannot restore the mission's data files: {exc}") from exc

Note de onde vem prepared.files. Não do Mission — o execute() não recebe a missão, e mudar a assinatura dele quebraria o protocolo Runner que existe justamente para que adicionar Java seja um arquivo novo e não um refactor. Os arquivos viajam no PreparedCode, que é o objeto cujo trabalho é atravessar de prepare() até execute().

E o erro é levantado, não devolvido como resultado. Sandbox que não aceita escrita é problema nosso, não do jogador. Reprovar a submissão dele por causa de um disco cheio seria mentir sobre quem errou.

6.4 O teste que prova o replantio

tests/unit/test_runner.py

def test_a_declared_file_is_planted_fresh_for_every_case(runner):
    source = (
        "def double(n):\n"
        "    with open('log.txt', 'a', encoding='utf-8') as handle:\n"
        "        handle.write('x')\n"
        "    return open('log.txt', encoding='utf-8').read()\n"
    )
    prepared = _prepare_with_files(runner, source, (("log.txt", "seed:"),))
    try:
        first = runner.execute(prepared, TestCase(args=(1,), expect=""), FAST)
        second = runner.execute(prepared, TestCase(args=(1,), expect=""), FAST)
    finally:
        runner.cleanup(prepared)

    assert first.returned == "seed:x"
    assert second.returned == "seed:x"

O second.returned == "seed:x" é a asserção inteira da feature. Sem replantio ela seria "seed:xx". É um teste de duas linhas de expectativa que vale mais do que a implementação: se alguém remover o replantio por achar redundante, este teste explica em segundos por que ele existia.

7. A ponte com AI Engineering

[AI-ENG:path-traversal]

Um agente com ferramenta de escrita em disco recebe o filename dentro do JSON da tool call — ou seja, gerado por um modelo, a partir de um prompt que pode conter texto de um documento recuperado, de um e-mail, de uma página web. É exatamente a mesma topologia desta fase: valor não confiável → caminho de escrita. E a mesma defesa: rejeite a tool call inteira quando o nome não for a forma que você espera. Não "conserte" o caminho e execute.

[AI-ENG:schema-validation]

O bloco files: entrou no mesmo validador que já cuidava do resto do schema, com o mesmo padrão: acumular todos os problemas e reportar de uma vez. É o formato de um validador de structured output. Um modelo que devolve JSON quase certo precisa de um relatório completo do que está errado para conseguir corrigir numa segunda passada — parar no primeiro erro transforma uma correção em cinco rodadas de ida e volta, e cada rodada custa tokens e latência.

[AI-ENG:sandboxing]

O sandbox agora tem estado, e estado precisa de política de reset. Um code interpreter que reaproveita o container entre chamadas está no mesmo lugar: os arquivos que a chamada anterior escreveu ainda estão lá. Ou você garante o estado inicial, ou o resultado da chamada N depende do que aconteceu na chamada N-1 — e debugar isso depois de entregue é caro.

[AI-ENG:blocklist-vs-allowlist]

Mesma lição da Fase 1, campo novo. Enumerar o proibido é uma aposta contra um conjunto infinito. Aqui a regra ficou allowlist na prática: um nome só passa se for um segmento simples, e todo o resto do universo de strings é recusado sem análise.

8. Exercício de fixação

Um colega escreveu esta função para um endpoint que serve arquivos de um diretório de uploads. Ele diz que testou com ../../etc/passwd e que a função barrou. 

UPLOADS = Path("/srv/app/uploads")

def read_upload(name: str) -> str:
    safe = name.replace("../", "")
    return (UPLOADS / safe).read_text()

Encontre três entradas diferentes que escapam do diretório, e depois reescreva a função seguindo o princípio desta aula. Não olhe a resposta antes de escrever as três no papel.

Ver a resposta

As três (há mais):

  1. "....//....//etc/passwd" — o replace remove os dois "../" internos e produz "../../etc/passwd". O saneamento construiu o ataque.
  2. "/etc/passwd" — não contém "../", então o replace não faz nada. E Path("/srv/app/uploads") / "/etc/passwd" devolve PosixPath('/etc/passwd'): o segmento absoluto descarta o prefixo.
  3. "..%2Fetc%2Fpasswd" — se qualquer camada adiante fizer URL-decode, isso vira "../etc/passwd" depois de já ter passado pela validação. Validar antes de normalizar é validar outra string.

A reescrita:

UPLOADS = Path("/srv/app/uploads")


def read_upload(name: str) -> str:
    """Ler um upload pelo nome. Recusa qualquer coisa que não seja um nome simples."""
    if not name or "/" in name or "\\" in name or ":" in name or name.startswith("."):
        raise ValueError(f"nome de upload inválido: {name!r}")
    return (UPLOADS / name).read_text(encoding="utf-8")

Nada é consertado. A função ou recebe um nome simples, ou não atende. E repare que name!r mostra o nome com aspas e escapes visíveis — num log, '..\\x' é legível e ..\x pode virar tabulação.

A variante com resolve(), e por que ela é pior aqui:

alvo = (UPLOADS / name).resolve()
if not alvo.is_relative_to(UPLOADS.resolve()):
    raise ValueError(...)

Funciona, e às vezes é a resposta certa — quando subdiretórios são legítimos. Mas ela é mais fraca por natureza: depende de resolve() se comportar igual em todo sistema de arquivos, atravessa symlinks, toca o disco, e responde "o resultado ficou dentro?" em vez de "a entrada era válida?". Quando um nome simples basta, a checagem de forma é mais forte e mais barata. Escolha a pergunta mais restritiva que ainda resolve o seu problema.

Bônus, se quiser ir além

O _plant_files desta fase escreve texto. Escreva no papel o que precisaria mudar para suportar um arquivo binário numa missão (uma imagem, um .zip) e qual novo problema de validação isso cria.
